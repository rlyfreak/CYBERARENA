# Публикация CRYPTO-01

## Условие для карточки

- **Код:** `CRYPTO-01`
- **Название:** `Повторяющаяся маска`
- **Категория:** `Crypto`
- **Сложность:** `easy`
- **Баллы:** `150` (значение закреплено действующим CTF Core)
- **Ресурс:** `/files/crypto-01/challenge.txt`

Текст описания для копирования в админскую карточку:

> Перехвачена служебная записка CYBERARENA. Скачайте challenge.txt:
> её байты зашифрованы XOR с повторяющимся семибайтным ключом и записаны
> шестнадцатерично. Исходное сообщение начинается ровно с
> `CYBERARENA INCIDENT REPORT` и символа перевода строки. Восстановите ключ,
> расшифруйте записку и отправьте значение после `Access token:` в формате
> `CTF{...}`. Перебор не требуется.

## Подготовка файла

В репозитории уже лежит настоящий зашифрованный
`files/crypto-01/challenge.txt`. Строка `CYBERARENA CRYPTO-01 XOR DATA v1`
в его заголовке — безопасный marker для `CRYPTO01_EXPECTED_MARKER`; она не
содержит ответ.

Для пересоздания задания на Windows из корня репозитория:

```powershell
py -3.12 scripts/generate_crypto_01.py --output files/crypto-01/challenge.txt --replace
```

Команда запрашивает флаг и семисимвольный ASCII-ключ без их отображения.
При тех же входных данных получается идентичный файл. `--replace` разрешён
только при сознательном переиздании задания **до** публикации; без него
генератор не перезаписывает готовый материал. Исходные значения держите в
закрытом хранилище организатора. Для уже созданного файла их можно
восстановить из шифртекста по write-up, поэтому отдельный файл с секретом
в репозитории не нужен. Никогда не передавайте флаг аргументом командной
строки и не добавляйте его в `.env` или CI.

## Установка карточки через существующий CTF Core

1. В интеграции CRYPTO-01 используется файловая инфраструктура из PR #12
   без слияния draft PR #13. На целевом стенде убедитесь, что nginx отдаёт
   `/files/crypto-01/challenge.txt` с HTTP 200 и текстовым Content-Type.
   Merge кода не заменяет развёртывание: **не публикуйте карточку**, пока
   проверка настоящего файла на этом стенде не пройдена.
2. Выполните `docker compose exec app python -m app.ctf.cli --admin admin seed-case`.
   Команда идемпотентно создаст неопубликованный черновик CRYPTO-01, если
   его ещё нет. Имя `admin` замените фактическим именем администратора.
3. Откройте `/admin`, найдите идентификатор черновика CRYPTO-01 и перейдите
   в его редактирование. Заполните поля точно как указано выше. Для флага
   локально выполните пример решения из write-up и вставьте результат в
   скрытое поле админской формы. Включите «Опубликовано» только после
   проверки файла. Если черновик уже настроен, не меняйте его флаг.
4. Проверьте карточку авторизованным участником и выполните один полный
   прогон: неверный флаг, правильный флаг, повторная отправка, рейтинг.

Альтернативно шаг 3 можно выполнить CLI. Подставьте реальный идентификатор
черновика вместо `<ID>`; команда запросит флаг скрытым вводом:

```powershell
docker compose exec app python -m app.ctf.cli --admin admin edit <ID> --title "Повторяющаяся маска" --description "Перехвачена служебная записка CYBERARENA. Скачайте challenge.txt. Байты зашифрованы XOR с повторяющимся семибайтным ключом и записаны шестнадцатерично. Исходное сообщение начинается ровно с CYBERARENA INCIDENT REPORT и символа перевода строки. Восстановите ключ, расшифруйте записку и отправьте значение после Access token: в формате CTF{...}. Перебор не требуется." --category Crypto --points 150 --difficulty easy --resource-url /files/crypto-01/challenge.txt --set-flag --publish
```

CLI использует существующий метод обновления: повторное `seed-case` не
меняет карточку и результаты. Повторный `edit --set-flag` без необходимости
не запускайте.

## Передача Полине и проверка nginx

Передайте Полине эту ветку или PR и путь `files/crypto-01/challenge.txt`.
Публикуется **только** содержимое `files/`. `docs/CRYPTO-01-writeup.md` и
исходники генератора не должны попадать в nginx mount.

После появления маршрута запустите на общем стенде:

```powershell
python scripts/check_static_files.py --base http://127.0.0.1:8080 --root files
python scripts/check_crypto_01_resource.py --base http://127.0.0.1:8080
$env:CRYPTO01_RESOURCE_PATH = "/files/crypto-01/challenge.txt"
$env:CRYPTO01_EXPECTED_MARKER = "CYBERARENA CRYPTO-01 XOR DATA v1"
```

Для `scripts/check_resource_integration.py` также обязательны реальные
`WEB02_RESOURCE_PATH` и `WEB02_EXPECTED_MARKER`; скрипт следует запускать
после появления WEB-02. Отсутствие переменных должно завершаться ошибкой.
Проверьте HTTP 404 для несуществующего файла, текстовый Content-Type,
отсутствие доступа к write-up через `/files/` и скачивание без JavaScript.
Текущий frontend открывает текстовый ресурс в новой вкладке. Если продукту
нужно именно принудительное скачивание, Полине потребуется согласовать
`Content-Disposition` в nginx; сам файл уже доступен для сохранения.

Истинная готовность К-2 требует также WEB-02, обеих публикаций и общего QA
Алины. Тестовые fixtures из PR #13 не заменяют эти материалы.

## Воспроизводимая проверка CI

CI сохраняет исходные checker-скрипты и сначала проверяет HTML/JS/TXT
из `scripts/fixtures/files` вместе с CTF Core, изоляцией и перезапуском.
Этот этап не доказывает готовность настоящего WEB-02.

Затем `compose.crypto-test.yaml` заменяет только файловый mount nginx
на настоящий `files/` в том же изолированном тестовом проекте.
`check_static_files.py --root files` и `check_crypto_01_resource.py`
проверяют точные байты, заголовки и недоступность write-up.
`check_crypto_01_flow.py prepare` проверяет карточку с настоящим ресурсом,
неверный ответ, правильный ответ и однократные 150 баллов. После
перезапуска приложения `check_crypto_01_flow.py verify` проверяет
сохранность карточки, решения и рейтинга. Ответ восстанавливается только
в памяти и не выводится в CI. Скрипт использует локальный тестовый порт
18080 и тестовые аккаунты `ctf_smoke.py`; для production он не предназначен.

Frontend-изменения draft PR #13 остаются отдельной работой. До настоящего
WEB-02 и общего QA К-2 открыт даже при зелёном CRYPTO-01 CI.
