## Найденный дефект Auth

Передача не-ASCII CSRF-токена, например `тест`, в `secrets.compare_digest`
для строк вызывает `TypeError`. Воспроизведено непосредственным вызовом
обработчика регистрации до обращения к базе. Такой запрос должен получать 403.
Одинаковый способ сравнения используется в остальных Auth-обработчиках.

Первый коммит с кодом должен вынести безопасную проверку CSRF в общий модуль
и проверить отсутствующие, неверные и не-ASCII токены во всех изменяющих
Auth-маршрутах. Эту же проверку использовать в CTF API и HTML-формах.

## Инварианты данных

1. `Solve` имеет внешние ключи и ограничение базы
   `UNIQUE(user_id, challenge_id)`. Проверка в Python не заменяет ограничение.
2. Баллы фиксируются в `Solve.points_awarded` при первом решении.
   Рейтинг считается по `SUM(Solve.points_awarded)`; отдельный изменяемый
   счётчик баллов у пользователя не нужен.
3. Попытка и новое решение сохраняются одной транзакцией. Ошибка записи
   не может оставить начисление без попытки или попытку успеха без решения.
4. Повторный запрос создаёт запись истории с результатом `already_solved`,
   но не создаёт второй Solve и не меняет баллы или время первого решения.
5. Решение записывается через SQLite INSERT ON CONFLICT по конкретному
   уникальному ограничению. Результат вставки определяет начисление.
   Другие ошибки целостности не маскируются как повторное решение.
6. История сохраняет результат и время, но не исходный флаг.
   Результаты: `incorrect`, `correct`, `already_solved`, `invalid_format`.
   Запросы без сессии, с неверным CSRF и транспортно некорректные запросы
   отклоняются до создания игровой попытки.
7. Только опубликованные задания доступны участнику и принимают ответы.
   Прямой запрос к скрытому заданию возвращает 404.
8. Снятие публикации и изменение стоимости не отменяют ранее заработанные баллы.

## Модели и совместимая миграция

- Расширить существующий `Challenge`: `is_published` с безопасным default false.
  Существующие поля и идентификаторы сохранить.
- Расширить `Submission` полем результата, сохранив `is_correct` для совместимости.
  Для старых записей результат вывести из `is_correct`.
- Добавить `Solve`: id, user_id, challenge_id, points_awarded, solved_at,
  ссылка на первую успешную попытку; положительные баллы и UNIQUE пары.
- Время новых решений фиксировать в UTC с микросекундами после получения права
  записи, а не при начале HTTP-запроса. Не полагаться на секундную точность
  SQLite CURRENT_TIMESTAMP для разрешения ничьих.
- Добавить индексы для истории пользователя и агрегирования решений.
- Миграция должна работать на пустой базе, старой схеме и при повторном запуске.
  Не удалять и не пересоздавать рабочие таблицы для добавления столбцов.
- Для старых правильных попыток предусмотреть один Solve на пару по самой ранней
  успешной попытке. Старые исторические стоимости в схеме отсутствуют:
  восстановление возможно только по текущей стоимости с явной документацией.
  В проверенной рабочей базе таких попыток сейчас нет.
- Не переопределять алгоритм существующих `flag_hash` по длине строки.
  Хэши неизвестного формата сохранить; публикацию таких заданий блокировать
  до установки поддерживаемого хэша. В рабочей базе заданий сейчас нет.

## Границы модулей

  Отдельные ORM, JWT, Redis, Celery и новая инфраструктура не нужны.

## Проверка флагов и защита запросов

- Установить точный формат `CTF{...}`: непустое содержимое, без вложенных
  скобок, пробелов и управляющих символов; ограничение общей длины 256 символов.
  Регистр значим; не делать strip, lower или Unicode-нормализацию.
- Использовать солёные Argon2-хэши через уже имеющийся pwdlib; расширить
  объявленный тип flag_hash для кодированного хэша. В SQLite ограничение длины
  VARCHAR не применяется, поэтому отдельно проверить старую схему тестом.
- Ограничить частоту попыток в общей SQLite по пользователю, а также
  потребление ресурсов дорогой проверки с учётом лимита app 512 MiB.
  Проверку хэша выполнять вне долгой блокировки записи SQLite.
- После проверки хэша транзакция должна повторно проверить публикацию и
  актуальность данных задания перед записью результата.
- Конкурентные корректные запросы: один `correct`, остальные `already_solved`.
  Конкурентные неверные попытки не должны теряться.
- Блокировки SQLite обрабатывать ограниченным ожиданием/повтором транзакции;
  после исчерпания вернуть 503 с Retry-After. Не повторять частичные операции.
- Удалить флаг из сообщений ошибок валидации: стандартный ответ FastAPI может
  включать исходный input. Не писать тела отправок в логи и не отражать флаг в HTML.
- Историю выдавать только её владельцу. Для форм и API обязателен CSRF;
  для персональных ответов и выдачи CSRF использовать Cache-Control: no-store.
- Cookie Secure не включать безусловно: существующая установка работает по HTTP.
  HTTPS-настройка потребует отдельного согласованного изменения окружения.

## API и страницы

Предлагаемый контракт:

| Метод | Путь | Поведение |
| --- | --- | --- |
| GET | /api/challenges | Каталог опубликованных заданий, категория, пагинация; требуется вход |
| GET | /api/challenges/{id} | Описание, категория, баллы, состояние решения; требуется вход |
| POST | /api/challenges/{id}/submissions | JSON-флаг, серверная сессия, CSRF в заголовке |
| GET | /api/submissions | Только собственная история, пагинация |
| GET | /api/leaderboard | Публичный рейтинг с пагинацией |
| GET | /api/csrf | Токен для текущей сессии, no-store |
| GET | /challenges | Jinja2-каталог |
| GET/POST | /challenges/{id} | Страница задания и отправка формы с CSRF |
| GET | /submissions | Собственная история |
| GET | /leaderboard | Публичная таблица лидеров |

POST: 200 для проверенного правильного/неправильного ответа, 409 для
`already_solved`, 422 для неверного формата, 429 при ограничении частоты;
401/403/404 для отказа в доступе. Успешные HTML-формы используют redirect 303.

Для загрузки заданий добавить небольшую административную CLI-команду:
проверка всех полей, ввод флага без отображения в терминале, сохранение хэша,
создание и изменение публикации. Флаг не передавать аргументом командной строки
и не включать в Git. Полную административную панель в этот этап не включать.

Рейтинг: баллы по убыванию, время последнего успешного решения по возрастанию,
user_id как стабильный последний критерий при точном совпадении времени.
Рейтинг включает обычных участников, в том числе с нулевыми баллами;
администраторы исключены. Места вычисляются до пагинации.

## Логические коммиты и проверки

1. `fix(auth): reject malformed csrf tokens consistently`
   Общий CSRF и регрессионные тесты; весь существующий Auth-набор остаётся зелёным.
2. `feat(ctf): add compatible schema migration and solve model`
   Ограничения базы, повторная миграция, сохранность пользователей/сессий,
   старых заданий/попыток и перенос дубликатов старых успехов.
3. `feat(ctf): verify flags and award solves atomically`
   Хэширование, история, ограничение попыток и транзакции. Тесты повторов,
   отката при ошибке и конкуренции на файловой SQLite с отдельными соединениями.
   Проверить конкуренцию также между отдельными процессами.
4. `feat(ctf): expose catalog submissions and leaderboard api`
   Авторизация, CSRF, скрытые задания, отсутствие утечек, чужая история,
   сортировка ничьих, нулевые баллы, администраторы и пагинация.
5. `feat(ctf): add participant pages and challenge management cli`
   Общий сервис для HTML/API, экранирование пользовательского текста,
   отсутствие флага в ответах, ссылки с главной и профиля.
6. `test(ctf): verify docker startup migration and isolation`
   Python 3.12 в отдельном тестовом образе: Ruff, Pytest, pip check.
   Отдельный Compose-проект, уникальные имена образов, другой localhost-порт,
   собственный том SQLite и тестовые секреты только в окружении процесса.
   Проверить запуск с пустой/старой базой, перезапуск, сохранность решений,
   nginx, /lab/ и изоляцию WEB-01. Рабочий стек не перезапускать.

После каждого коммита сообщать изменения и фактически пройденные проверки.
Тяжёлые зависимости не добавлять. Merge и публикацию изменений не выполнять.

## Условия готовности

- На все перечисленные инварианты есть автоматические проверки.
- Параллельные отправки дают ровно один Solve и одно начисление.
- Сбой не оставляет частичный результат; повтор после потери ответа безопасен.
- Миграция сохраняет старые данные и выдерживает повторный запуск.
- Ruff, Pytest и pip check проходят на целевом Python 3.12 в Docker.
- Через nginx работают новые страницы и API; WEB-01 сохраняет изоляцию.
- В исходной рабочей папке сохранены локальные изменения; `.env`, реальные
  секреты, рабочий том базы и текущие контейнеры не изменены.
