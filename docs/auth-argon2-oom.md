# В-1: память Argon2 и устойчивость авторизации

## Причина и границы исправления

`pwdlib.PasswordHash.recommended()` в проверенной версии использует Argon2id
с `memory_cost=65536 KiB`, `time_cost=3`, `parallelism=4`. До исправления
синхронные маршруты `/login`, `/register` и `/change-password` могли
одновременно выполнять много таких операций в пуле потоков FastAPI. Проверка
несуществующего логина тоже выполняет Argon2 через `_DUMMY_HASH` и нужна для
снижения различий во времени ответа. Блокировка по логину не мешает посылать
запросы с разными именами. Лимит приложения в Compose — 512 MiB, 1 CPU,
один процесс Uvicorn.

## Реализация

- `auth.security.PasswordOperationLimiter` допускает одновременно 2 операции
  `hash_password`/`verify_password` и не более 8 ожидающих. Ожидание слота
  длится не более 2 секунд. Любой выход из операции освобождает занятые ею
  слоты; переполнение выбрасывает `PasswordCapacityError`. Все вызовы Argon2
  в Auth проходят через эти две функции: регистрация, вход, смена пароля,
  начальный администратор и
  проверка `_DUMMY_HASH`.
- HTML-формы возвращают 503 с `Retry-After: 1` и понятным сообщением, если
  слот недоступен. Отказ при регистрации или смене пароля не сохраняет
  частичную запись. Ответы не содержат паролей, хешей или traceback.
- Публичные POST `/login` и `/register` используют общий для процесса
  потокобезопасный бюджет: всплеск 32 запроса, пополнение 4 запроса/с.
  Превышение даёт 429 с `Retry-After`. Он проверяется после CSRF и валидации
  простых полей, перед обращением к SQLite и Argon2. Бюджет одинаков для всех
  логинов и не читает `X-Forwarded-For`: адрес клиента за текущим nginx не
  является надёжной основой для индивидуального ограничения.
- Устаревшие записи `LoginAttempt` удаляются при очередной неудачной попытке
  не чаще раза в минуту. Активная блокировка не удаляется. Это ограничивает
  рост SQLite от потока уникальных несуществующих имён.
- Смена пароля обновляет строку пользователя только если сохранённый хеш
  всё ещё равен проверенному. Проигравший параллельный запрос получает 409 и
  не перезаписывает пароль, установленный первым запросом.

Стоимость Argon2, существующая блокировка по логину, CSRF, серверные сессии и
политика паролей не менялись. Лимиты действуют внутри одного процесса; если
число workers изменится, общий предел станет кратен их количеству, и
конфигурацию нужно пересмотреть.

## Воспроизведение на Windows

В PowerShell, в корне репозитория, задать **только тестовые** значения и
выполнить команды ниже. Если доступен Python Launcher, вместо `python`
можно использовать `py -3.12`.

```powershell
$env:CTF_CHECK_ADMIN_PASSWORD = 'IsolatedAuthOomAdminPass2026'
$env:CTF_CHECK_SESSION_SECRET = 'cyberarena-auth-oom-isolated-session-secret-2026'
$env:CTF_CHECK_WEB01_FLAG = 'CTF{isolated_auth_oom_web01_test}'
docker compose --env-file .env.example -f compose.ctf-test.yaml -p cyberarena-auth-oom up -d --build --wait
python scripts/auth_load.py --project cyberarena-auth-oom --scenario unknown --clients 16
python scripts/auth_load.py --project cyberarena-auth-oom --scenario unknown --clients 32
python scripts/auth_load.py --project cyberarena-auth-oom --scenario wrong --clients 16
python scripts/auth_load.py --project cyberarena-auth-oom --scenario correct --clients 32
python scripts/auth_load.py --project cyberarena-auth-oom --scenario register --clients 32
python scripts/auth_load.py --project cyberarena-auth-oom --scenario correct --clients 16 --distinct-users --arrival-seconds 3 --retry-503 2
docker compose --env-file .env.example -f compose.ctf-test.yaml -p cyberarena-auth-oom down
```

Скрипт принимает только проект `cyberarena-auth-oom` и локальный порт 18080.
Он создаёт случайные тестовые учётные записи, не печатает пароли и запускает
ограниченную волну. `--distinct-users` создаёт отдельную учётную запись и
сессию для каждого успешного входа; после подготовки бюджет публичных POST
восстанавливается. `--arrival-seconds` равномерно распределяет первые запросы,
а `--retry-503` выполняет до двух повторов только после 503 с задержкой не
менее секунды. Поля `statuses` и `p95_ms` относятся к первым запросам,
`final_statuses` — к результату после повторов. Скрипт завершает работу с
ошибкой при HTTP 500/502/504,
таймауте, OOM, перезапуске, недоступности приложения, отсутствии ожидаемого
ответа или невозможности снова войти после всплеска. Состояние приложения,
память и CPU читаются из cgroup тестового контейнера. `memory.peak` включает
подготовку учётных записей после последнего перезапуска приложения; это
консервативный пик для сценария, а не только интервала отправки запросов.
Для сравнения
сценариев приложение перезапускалось **только в этом Compose-проекте** перед
каждой волной; тестовый volume сохранялся. После проверки удалить только
собственный том `cyberarena-auth-oom_ctf-check-db`, если он более не нужен.

## Исходный замер 21.10.2026: очередь 4, ожидание 1 с

Docker Desktop Linux, Compose `app`: 512 MiB, 1 CPU, один Uvicorn worker.
Волна содержит один POST на клиента; p95 относится к HTTP-времени всей
волны, включая ожидающих. `memory.peak` — показатель cgroup после волны;
среднее — выборка `memory.current` примерно раз в 0,2 с. CPU — изменение
`cpu.stat usage_usec` за интервал теста относительно одного ядра.

Все контрольные контейнеры оставались запущенными, число новых перезапусков
равнялось нулю, `/api/health` отвечал 200, CTF API возвращал ожидаемый 401
для неавторизованного клиента. `PRAGMA integrity_check` настоящей тестовой
SQLite-базы вернул `ok`. Два ответа 429 в сценарии неверного пароля
вызваны существующей блокировкой атакуемой учётной записи. Проверка
восстановления всегда использовала отдельную тестовую учётную запись.

Сопоставимого собственного замера **до исправления** нет: нагрузка старой
версии при 512 MiB могла бы завершить контейнер по OOM. Оценка Полины около
655 МБ при десяти проверках — контекст аудита, не результат этого прогона.
Один ограниченный замер не доказывает устойчивость к любой нагрузке.

## Дополнительный замер 21.10.2026: очередь 8, ожидание 2 с

Те же 512 MiB, 1 CPU, один Uvicorn worker и Argon2id 65536 KiB / 3 / 4.
Перед каждой волной перезапускалось **только** приложение отдельного
Compose-проекта; SQLite-volume сохранялся. Входы с `--distinct-users` используют
разные зарегистрированные аккаунты и независимые cookie/CSRF-сессии.
В колонке «Ответы» приведены первые запросы; p95 измеряет их HTTP-время.

| Сценарий | Клиенты | Ответы | p95 мс | Пик MiB | CPU | OOM / новые перезапуски |
|---|---:|---|---:|---:|---:|---|
| Одновременный правильный вход | 5 | 303: 5 | 1047 | 192,88 | 71,1% | 0 / 0 |
| Одновременный правильный вход | 10 | 303: 10 | 2141 | 194,21 | 85,7% | 0 / 0 |
| Одновременный правильный вход | 16 | 303: 8, 503: 8 | 2469 | 201,45 | 85,4% | 0 / 0 |
| Одновременный правильный вход | 32 | 303: 12, 503: 20 | 2593 | 196,78 | 83,5% | 0 / 0 |
| Одновременная регистрация | 5 | 200: 5 | 985 | 193,13 | 71,6% | 0 / 0 |
| Одновременная регистрация | 10 | 200: 10 | 2171 | 200,07 | 85,2% | 0 / 0 |
| Одновременная регистрация | 16 | 200: 10, 503: 6 | 2297 | 201,24 | 85,5% | 0 / 0 |
| Одновременная регистрация | 32 | 200: 11, 503: 21 | 2687 | 206,80 | 85,9% | 0 / 0 |
| Разные неизвестные логины | 32 | 401: 11, 503: 21 | 2656 | 205,94 | 88,5% | 0 / 0 |
| 16 участников, входы за 3 с | 16 | 303: 16 | 671 | 204,03 | 87,1% | 0 / 0 |

При исходной очереди 4/1 строго одновременные 10 входов дали 303: 6 и
503: 4 (p95 1313 мс, пик 194,62 MiB); те же четыре клиента вошли после
одного повтора с задержкой 1,1 с. Распределённые 10 входов за 3 с дали
303: 10, 429: 0, 503: 0 (p95 265 мс, пик 138,22 MiB); 16 входов за 4 с
дали 303: 16 (p95 265 мс, пик 139,88 MiB). Увеличение **только** очереди и
времени ожидания сохраняет два рабочих Argon2-слота и существенно снижает
отказы при синхронном входе десяти участников ценой более длинного p95.
При отдельной волне 16 строго одновременных входов первые ответы были
303: 10 и 503: 6; шесть повторов через 1,1 с завершились 303, то есть
итоговые ответы — 303: 16. Эта волна дала максимальный наблюдавшийся пик
208,49 MiB и запас 303,51 MiB до лимита 512 MiB. Тестовая SQLite после
нагрузки вернула `PRAGMA integrity_check = ok`; приложение вновь отвечало
200 на `/api/health`, а отдельный участник мог войти. При 16–32 строго
одновременных запросах ограниченные
503 остаются ожидаемым поведением. Общий бюджет 32/4 не вызвал 429 в
измеренных обычных сценариях; он сохраняется для защиты от потока запросов.

## Оставшиеся риски и интеграция

- Атакующий всё ещё может намеренно заблокировать известный логин
  администратора пятью неверными попытками. Нужна отдельная задача с
  доверенным адресом клиента на границе nginx и переоценкой политики
  блокировки; отключать её в этом PR небезопасно.
- Общий бюджет запросов может временно отказать добросовестным пользователям
  при длительной атаке. Из-за отсутствия надёжной клиентской идентичности
  он является предохранителем ресурсов, а не полной защитой от DoS.
- Быстрые тесты `backend/tests/test_auth_capacity.py` попадают в текущий CI
  автоматически. Нагрузочный скрипт запускается вручную на выделенном стенде.
  PR #13 также меняет `backend/tests/test_auth.py`, поэтому после его
  объединения требуется проверить совместимость общей тестовой фикстуры и
  повторить полный CI. С PR #14 пересечений по файлам нет. Продакшен
  Compose и nginx для этого исправления менять не требуется.
