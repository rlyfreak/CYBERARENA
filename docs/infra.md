# Инфраструктура CYBERARENA

Платформа запускается через Docker Compose на [http://localhost:8080](http://localhost:8080).
Все команды выполняются из корня репозитория. Нужны Docker с Compose и Python
для генерации секрета.

## 1. Первый запуск

1. Скопируйте `.env.example` в `.env`:

   ```text
   cp .env.example .env
   ```

   В PowerShell: `Copy-Item .env.example .env`. Копирование нужно только для
   новой установки. Не перезаписывайте существующий `.env` при обновлении.

2. Откройте `.env` в локальном редакторе. Установите `ADMIN_PASSWORD` длиной
   **12–128 символов**. Значение `ADMIN_USERNAME=admin` можно оставить.
3. Сгенерируйте случайный ключ подписи сессий:

   ```text
   python -c "import secrets; print(secrets.token_urlsafe(48))"
   ```

   Вставьте результат в `SESSION_SECRET` в `.env`; требуется **минимум 32 символа**.
   Результат команды — настоящий секрет: не публикуйте его, не сохраняйте в
   отчётах или логах CI. Храните `.env` локально с доступом только у ответственных
   за установку. Для резервной копии секретов используйте защищённое хранилище.
4. Сгенерируйте `WEB01_FLAG` в формате `CTF{...}` и внесите его в `.env`:

   ```text
   python -c "import secrets; print('CTF{' + secrets.token_hex(12) + '}')"
   ```

   Этот же флаг затем введите в закрытое поле карточки WEB-01 в `/admin`.
   Пустое значение не позволит запустить лабораторию.
5. Соберите и запустите платформу:

   ```text
   docker compose up -d --build
   ```

6. Проверьте состояние всех четырёх контейнеров:

   ```text
   docker compose ps --all
   ```

   Дождитесь `healthy` у `app`, `nginx`, `lab-gateway`, `lab-web`. На первом
   запуске сборка может занять несколько минут. Для нездорового или завершившегося
   контейнера используйте команды из раздела диагностики.
7. Откройте [http://localhost:8080](http://localhost:8080).
   Войдите с выбранными ADMIN_USERNAME/ADMIN_PASSWORD. При первом входе
   администратор должен сменить начальный пароль.

**Шаблон содержит только публичные заглушки `REPLACE_WITH_YOUR_PASSWORD` и
`REPLACE_WITH_RANDOM_SECRET`. Замените обе до запуска. Приложение отклоняет
пароль-заглушку и SESSION_SECRET короче 32 символов.**

Настоящие `.env` и `.env.*` игнорируются Git; `.env.example` остаётся в репозитории.
Не добавляйте `.env` принудительно через `git add -f`. Не публикуйте вывод
`docker compose config` без `--quiet`: он может содержать подставленные секреты.
Для проверки структуры без вывода значений используйте `docker compose config --quiet`.

## 2. Сервисы и адреса

Внешний nginx находится только в app-net. Отдельный lab-gateway связывает
app-net и внутреннюю lab-net, но проксирует исключительно WEB-01; маршрута к
приложению в нём нет. WEB-01 работает без root и не получает том SQLite.

| Адрес | Что там |
| --- | --- |
| http://localhost:8080/ | Главная страница |
| http://localhost:8080/docs | Документация API |
| http://localhost:8080/api/health | Проверка бэкенда |
| http://localhost:8080/challenges | Каталог заданий после входа |
| http://localhost:8080/leaderboard | Публичный рейтинг |
| http://localhost:8080/admin | Управление для администратора |
| http://localhost:8080/lab/ | Учебная лаборатория |

## 3. Обновление и сохранность данных

Код и Jinja2-шаблоны уже входят в образ. После обновления backend или frontend:

```text
docker compose up -d --build
```

Ручное подключение Jinja2, главной страницы или маршрутов не требуется.
Без сборки новый код не попадёт в образ.

SQLite хранится в именованном томе `db-data`; перезапуск сохраняет пользователей,
сессии, задания, попытки и решения. Миграции выполняются автоматически при запуске.
Не удаляйте том для обновления. Перед обновлением используйте предусмотренные
проектом резервное копирование базы и отдельное защищённое хранение `.env`.

Сохраняйте существующие `.env` и `SESSION_SECRET`. Изменение ADMIN_PASSWORD в
окружении не меняет пароль уже созданного администратора; пароль меняется через
форму приложения. Смена SESSION_SECRET сделает текущие подписанные cookie
недействительными, даже если серверные сессии остаются в базе.

## 4. Перезапуск и остановка

| Задача | Команда |
| --- | --- |
| Перезапустить всё | `docker compose restart` |
| Перезапустить только приложение | `docker compose restart app` |
| Остановить с сохранением тома | `docker compose down` |

**`docker compose down -v` удаляет том SQLite и все находящиеся в нём данные.**
Это не команда обычной остановки или обновления. Без проверенной резервной
копии восстановить удалённые данные нельзя. Не применяйте её к рабочей установке.

## 5. Диагностика

| Задача | Команда |
| --- | --- |
| Состояние всех сервисов | `docker compose ps --all` |
| Проверка Compose без вывода секретов | `docker compose config --quiet` |
| Логи приложения | `docker compose logs -f app` |
| Последние логи всех сервисов | `docker compose logs --tail=100` |
| Оболочка приложения | `docker compose exec app sh` |

Не публикуйте `.env`, пароли, SESSION_SECRET и полный вывод конфигурации или
`docker inspect`. Проверяйте диагностические материалы перед передачей другим.

## 6. Частые проблемы

| Симптом | Что проверить |
| --- | --- |
| Compose требует ADMIN_PASSWORD или SESSION_SECRET | Скопирован ли шаблон и заполнены ли оба значения в `.env` |
| Приложение отклоняет пароль | Длина 12–128 символов, заменена ли публичная заглушка |
| Приложение отклоняет SESSION_SECRET | Случайный ключ длиной минимум 32 символа вместо заглушки |
| Не запускается lab-web | Проверьте `WEB01_FLAG` в `.env`: требуется непустой флаг формата `CTF{...}` |
| Порт 8080 занят | Проверьте уже работающую установку; не останавливайте её и не удаляйте данные для повторного запуска |
| Контейнер не healthy | Смотрите логи конкретного сервиса, сохраняя секреты в тайне |
| После правок остался старый код | Выполнена ли сборка с `--build` |
| Лаборатория недоступна | Проверьте lab-web и lab-gateway; приложение и рейтинг должны продолжать работать |

Для проверки изменений без воздействия на рабочую установку используйте
[отдельный тестовый стенд](ctf-verification.md). Управление заданиями описано в
[инструкции CTF Core](ctf-core.md).

## Дополнительно: HTTPS и защита main для публичного запуска

Этот раздел относится к возможному будущему публичному запуску. Учебный кейс
Школы 21 требует локальную демонстрацию на одном ноутбуке без интернета;
HTTPS и настройка GitHub ruleset не являются условиями приёмки MVP.

Локальный стенд на `127.0.0.1:8080` работает по HTTP: оставьте
`SESSION_COOKIE_SECURE=false` (значение по умолчанию). Для публичного доступа
нужен внешний TLS-терминатор с действительным сертификатом. Он должен принимать
только HTTPS, перенаправлять HTTP на HTTPS, передавать запросы на loopback
`127.0.0.1:8080` и не открывать этот порт извне. После проверки HTTPS задайте
`SESSION_COOKIE_SECURE=true` в существующем `.env` и пересоздайте **только app**
с сохранением `SESSION_SECRET` и тома базы. Проверьте в браузере атрибуты
`Secure`, `HttpOnly`, `SameSite=Lax` у cookie, а также регистрацию, вход, CSRF,
выход и лабораторию через конечный HTTPS-адрес. Ошибка в значении переменной
останавливает запуск приложения вместо молчаливого отключения `Secure`.
Не считайте настройку cookie заменой TLS или проверки прокси.

В GitHub для `main` следует включить ruleset/branch protection: запрет прямых
push и force-push, обязательный PR с ревью, актуальная ветка перед merge,
обязательные проверки `Backend / Python 3.12` и
`CTF / Docker, persistence and isolation`. Перед включением проверьте точные
имена checks на текущем PR и права команды, чтобы не заблокировать работу.
Изменение настроек репозитория требует отдельного согласования владельца.
