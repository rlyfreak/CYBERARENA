# CTF Core: эксплуатация и демонстрация

## Запуск

Основная команда остаётся `docker compose up -d --build` из корня репозитория.
Стек содержит app, nginx, lab-gateway и lab-web. Отдельный lab-gateway устраняет
обход изоляции, при котором лаборатория могла достигать приложения через nginx.
Платформа открывается на http://localhost:8080. Используется существующий `.env`;
в репозиторий не следует добавлять пароли, SESSION_SECRET или флаги заданий.
Том `db-data` хранит пользователей, сессии, задания, попытки и решения после
перезапуска. Команда `down -v` удаляет данные и не нужна для обновления.

Миграции запускаются перед обслуживанием запросов. Расширение существующих
таблиц выполняется транзакционно; старые пользователи и идентификаторы сохранены.
Старые успешные попытки переносятся в один Solve по самой ранней попытке
с текущей стоимостью задания: исторических стоимостей старая схема не содержит.
Маркер миграции исключает повторное начисление после сброса результатов.
Неизвестные форматы старых хэшей не трактуются как SHA-256 автоматически;
для публикации администратор должен установить поддерживаемый флаг.

## Пользователь

- Регистрация и вход: `/register`, `/login`.
- Каталог и карточка: `/challenges`, `/challenges/{id}`.
- Собственная история: `/submissions`.
- Публичный рейтинг: `/leaderboard`.

Формат — `CTF{...}`, 6–256 печатных ASCII-символов, без пробелов и вложенных
скобок. Регистр важен, пробелы не обрезаются. Флаги не сохраняются в истории,
не возвращаются в API, HTML и ошибках валидации.

Правильный ответ создаёт Solve с фиксированной стоимостью. Уникальность пары
пользователь/задание проверяет SQLite. Повторный ответ не меняет баллы и время
решения; история отмечает его как `already_solved`. Попытка и начисление
коммитятся вместе. Снятие публикации и изменение стоимости не отнимают уже
заработанные баллы. Администраторы в рейтинг не входят.

Рейтинг сортируется по баллам (больше — выше), затем по времени последнего
успешного решения (раньше — выше), затем по user_id при полном совпадении.
Участники с нулевыми баллами присутствуют. Номер места стабилен между страницами.
Все времена решений и попыток указаны в UTC.

## Управление в браузере

Войти под существующей учётной записью администратора и сменить начальный
пароль, если система этого требует. В профиле доступна ссылка `/admin`.

Минимальный административный интерфейс уже позволяет:

1. Создать задание: код, название, категория, стоимость, условие и флаг.
2. Изменить условие, название, категорию, стоимость и флаг. Пустое поле нового
   флага сохраняет текущий хэш. Код после создания не меняется.
3. Опубликовать или скрыть задание галочкой в редакторе.
4. Просмотреть историю всех участников: `/admin/submissions`.
5. Сбросить демонстрационные решения и попытки, введя `RESET DEMO RESULTS`.
   Сброс сохраняет пользователей, серверные сессии и задания.

Редактор использует версию задания: устаревшая форма получает 409 и не
перезаписывает чужие изменения. Сброс также требует актуальную версию состояния.
Проверка флага, пересекающаяся со сбросом или изменением задания, не может
начислить баллы на основании устаревших данных.

Кнопка «Добавить черновики заданий кейса» идемпотентно создаёт отсутствующие:

| Код | Категория | Баллы |
| --- | --- | --- |
| WEB-01 | WEB | 100 |
| WEB-02 | WEB | 150 |
| CRYPTO-01 | CRYPTO | 150 |

Черновики скрыты и не имеют настроенного флага. До демонстрации нужно добавить
условия, материалы и флаги, проверить решаемость и опубликовать задания.
В репозитории есть учебный WEB-01 и настоящие материалы WEB-02/CRYPTO-01.
`seed-case` создаёт только скрытые черновики: на каждом демонстрационном стенде
нужно проверить ресурсы, задать серверные флаги и опубликовать карточки.
Порядок и критерии указаны в [приёмке кейса](school21-acceptance.md).

Расширенная админ-панель может быть следующим этапом: фильтры по заданиям и
результатам, удобные сообщения об ошибках, предпросмотр и журнал действий.
До демонстрации обязательна ручная проверка всех пяти операций выше и готовности
трёх упражнений. CLI не является обязательным или единственным способом управления.

## API

API использует те же серверные сессии. После входа получить CSRF через
`GET /api/csrf`; для POST/PATCH отправлять заголовок `X-CSRF-Token`.

- `GET /api/challenges`, `GET /api/challenges/{id}`.
- `POST /api/challenges/{id}/submissions`: JSON `{"flag":"CTF{...}"}`.
- `GET /api/submissions`: только история текущего пользователя.
- `GET /api/leaderboard`: без авторизации.
- `GET/POST /api/admin/challenges` и `PATCH /api/admin/challenges/{id}`.
- `GET /api/admin/submissions`, необязательный фильтр user_id.
- `GET /api/admin/results` — generation для подтверждения сброса.
- `POST /api/admin/results/reset`: confirmation и expected_generation.

Поля и схемы доступны в `/docs`. PATCH требует expected_revision из карточки.
Списки принимают offset >= 0 и limit от 1 до 100. Ошибки не содержат исходного флага.
Коды отправки: 200 — correct/incorrect; 409 — already_solved или конфликт
состояния; 422 — invalid_format; 429 — лимит попыток; 503 с Retry-After —
занята база или доступная ёмкость проверок. При 503 повторять с паузой.
Нельзя обходить CSRF для браузерной сессии ради удобства API.

## Ресурсы проверки флагов

Флаги хранятся в виде солёного Argon2id: 32 MiB, 3 прохода, parallelism=1.
Одновременно разрешены две проверки/операции создания хэша на всю SQLite-базу,
включая разные процессы приложения. Резервирование ёмкости и лимит 20 принятых
попыток за 60 секунд на пользователя выполняются перед Argon2. Некорректные
форматы и повторы тоже расходуют лимит. Занятость ёмкости не расходует попытку.
После аварии резерв освобождается через 60 секунд. Не увеличивать число
проверок или стоимость Argon2 без измерения в контейнере с лимитом 512 MiB.

## Дополнительная CLI

Внутри контейнера доступна `python -m app.ctf.cli --admin <username> --help`.
Команды: seed-case, create, edit. Флаг вводится скрыто через getpass, а не
аргументом процесса. Нужен существующий администратор со сменённым паролем.
Локальный доступ к CLI и базе равносилен административному доступу к хосту.
